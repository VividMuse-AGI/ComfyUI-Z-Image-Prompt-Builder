## 2. 本次发现

### F1：跨工作流延迟启动任务会误写当前同编号节点（P1，发布阻断）

证据位置：`web/js/prompt_diagnostics.js` 的 `acceptResult`、`execution_start` 和 `executed` 监听器。

目前用任务开始顺序及节点配置时的顺序阈值拒绝旧结果，收到结果时通过**当前** `app.graph.getNodeById()` 找节点，未将任务绑定到提交时的工作流／节点实例。

本轮借用现有前端测试的 VM 框架做未落盘探针：

1. 建立节点 ID 1 并接收一次正常结果。
2. 调用 `onConfigure()` 模拟切换／重新装载工作流，清空历史。
3. 此后才收到旧工作流任务的 `execution_start`。
4. 再收到该任务节点 ID 1 的 `executed`。
5. 实际：当前节点接收了“另一工作流结果”，显示“随机 1 项 · 查看上次结果”。预期：不得写入当前工作流节点。

这是**已复现的事件路由缺口**，不是已经在真实 ComfyUI 队列中完成的复现。现有测试只模拟 `execution_start → onConfigure → executed`，遗漏 `onConfigure → execution_start → executed`。

修复方向：按提交请求建立 `prompt_id → 工作流／节点实例` 的关联；缓存、切图、重连和宿主转发节点 ID 应使用同一归属规则。不能仅提高时间阈值，也不能通过比对选项相同就推断任务属于当前工作流。具体接入点须按本地宿主代码确认，不预设某个宿主事件必然存在。

### F2：历史变更提示只检查本节点控件（P2，语义边界待补测）

`stale()` 只比对历史 `settings` 与当前可序列化 widget，不读取上游变化；`comparison()` 则在下次执行后比较两次 `context`。因此“上游已改、下游未运行”与“下游新结果不可比较”是两种不同状态，不能混为已覆盖。

当前面板注明“上次实际执行”，所以这不等于文本输出错误。需测试连接输入、上游修改和断开重连是否误报／漏报“设置已修改”；依据实际能力标注“上次结果，未核对上游变化”，或可靠地追踪依赖变化。不要对已连接输入的旧控件值作错误比较，也不能为了诊断预执行上游。

### F3：验收记录有两处超出证据的表述

- 同一页面刷新后曾看到旧记录；全新页面恢复正常，只能证明新页面及保存文件未持久化历史，不能证明原刷新行为已经解释清楚。
- 源码有 `onRemoved` 关闭弹窗钩子，但当前诊断前端测试只调用了关闭按钮，未实际调用 `onRemoved` 断言移除。此前“删除节点由自动化覆盖”不准确，本轮已修正文档。

### F4：其他补测项，不直接认定为缺陷

- `executed` 使用 `display_node ?? node`，但现有诊断用例未覆盖真实子图中的嵌套节点定位。
- 未单独覆盖执行失败／中断、断线重连、128 条任务顺序记录淘汰和缺少事件 API 的回退路径。
- 历史限制为 5 条记录，不是字节上限；元数据包含输入与中英文全文。需测长文本及八模块串联的重复数据体积。浏览器历史不保存到工作流，不代表宿主执行历史不包含返回的 UI 元数据。
- 英文 `Random: 1 fields` 是单复数文案问题，可随针对性修复处理，不属于输出逻辑缺陷。
