# 发布前精简测试方案

日期：2026-10-07。范围：0.6.1 之后尚未提交的随机状态、执行结果诊断和保存修复。

本方案取代[上一版方案](2026-10-07-progress-review-and-final-test-plan.md)的后续执行顺序及发布门槛，不覆盖历史验收事实。原则：补齐已有疑点，复用有效证据；没有新异常，不扩展测试矩阵。

## 1. 基线与边界

- 已有干净副本通过 187 项 Python 测试、21 组前端回归、12 个 JS 语法检查、当前宿主 30＋9 次纯文本执行；旧宿主 0.31.1 的 30＋9 次后端执行另有记录。
- 当前前端的双语、经典／Nodes 2.0、TXT 保存恢复及代表子图用例已有证据，不重新全测。详见[验收记录](../testing/2026-10-07-follow-up-acceptance.md)。
- 上述是已有结果，不是本方案执行结果。开始测试先比较源码指纹；源码发生变化时，只能复用未受影响的证据。
- 使用我方独立纯文本工作流和 PreviewAny，不加载模型、不生图、不干扰现有队列。保留未保存保护；结束恢复用户界面设置及原工作流。
- 本次只制定方案，不自动授权提交、推送、Release、安装或修改运行环境。版本号另行确认。

## 2. 必测用例：先消除两个疑点

### F1：删除后撤销，是否保留输入

范围：摄影模块＋一个独立 TXT 节点，各在经典和 Nodes 2.0 下测试一次，共 4 个组合；不扩展到全部节点／语言。

1. 种子设为固定值，关闭执行后的种子变更。设置非默认字段、前置文本及连接；TXT 导入小词库并选择明确条目。
2. 完成控件编辑，保存删除前工作流 JSON，执行一次并记录输出。
3. 删除测试节点，执行 Ctrl+Z 恢复；保存恢复后的 JSON，比较业务字段、种子、词库内容、选择和连接。
4. 再执行，核对输出。忽略坐标等非业务差异；诊断历史允许清空，不要求被序列化。

通过：输入、连接及输出恢复一致，无字段错位。若失败，原样重复一次并用宿主原生节点作对照，定位宿主还是扩展问题。不得以重新导入成功替代撤销验收。

### F2：运行提交、种子和诊断结果是否一致

范围：一个完整节点，至少一个字段设为随机抽取，使用包含多个候选的字段；固定其他输入。当前布局执行即可，不再做双语全矩阵。

1. 顺序执行种子 41、42、41，等待每次提交确认并完成；核对重复 41 的实际输出可以复现。换种子偶尔相同是合法结果，不单独判错。
2. 快速提交 3 次并在提交之间编辑种子。记录每次实际请求的种子、返回的 prompt_id，以及对应服务输出和诊断记录。不要把按钮点击时的值当作已经提交的值。
3. 对照每个任务的输入、实际输出与面板种子／节点路径；最后显示应对应最新有效提交，不能串入其他任务。

通过：诊断与对应任务的真实输入／输出一致。若点击时种子与请求不同但面板忠实反映请求，记录宿主提交时序，不据此修改随机算法。若无法取得请求证据，标记未定并停止盲测，不增加到百次运行。

## 3. 兼容与交付检查

| 编号 | 内容 | 最小范围 | 通过标准 |
|---|---|---|---|
| F3 | 最低运行时 CI | 经授权推送后，由现有 Python 3.10／Node 22 CI 跑公开测试、语法及生成一致性 | 最终候选提交对应 CI 全绿；配置存在不算通过。不要求另搭本地最低版本环境 |
| F4 | 旧前端基本兼容 | 在可用的隔离旧环境记录宿主及前端版本；一张图放完整节点、摄影模块及两个 TXT 节点，检查加载、运行、保存重开后运行 | 字段及输出一致，主要按钮可用；旧宿主后端已通过，不再重复全部 CPU 验收。不要求旧前端拥有 Nodes 2.0 |
| F5 | 最终包与安装冒烟 | 核对公开文件、文档链接、版本／变更说明、秘密模式与 ZIP 根目录；授权后从正式附件安装，确认加载了候选脚本，运行一张代表文本图 | 无本地私有资料和漏打文件；11 个节点可注册，既有工作流能运行，保存重开正常，诊断与输出一致 |

F4 没有现成环境时，不自动安装或升级用户宿主。保留“旧后端已验证、旧前端未验证”的明确边界，发布前让用户决定是否接受该残余风险；不能宣称全版本 UI 已验收，也不自动无限延期。

F5 的缓存刷新只为确认新代码确实加载：普通刷新后能核对资源即足够；仍加载旧文件才进行强制刷新排查，不另设强刷专项。先完成候选包检查，再经授权推送并核对 CI，CI 通过后发布；正式附件安装作为发布后最后检查。

## 4. 暂缓项目与触发条件

以下不作为本次发布必过门槛：

- 堆快照、GC、旧图引用释放：仅当出现持续内存增长、页面逐步变慢或崩溃时专项调查；当前只能说明历史及关联数量有限，不能声称无内存泄漏。
- 再次百次压力测试：已有证据可复用；小样本发现随次数累积的问题时才扩大。
- 重跑全部语言／布局／子图矩阵：仅在相关代码修改、原用例失败或用户报告新问题时追加。
- 人为制造跨图长延迟：保留既有确定性回归，不插入阻塞任务干扰用户队列。

## 5. 修复、完成与停止规则

1. F1／F2 无异常后即停止该项，不为追求更多覆盖增加轮次。
2. 有可复现的输入丢失、输出错配、执行失败或明显持续性能恶化：保留最小复现，补定向回归，再修复；不做猜测式改动。
3. 仅更新文档：检查链接、最终文件清单与包哈希，不重跑运行测试。修改运行代码：先跑受影响回归，最终候选由 CI 做全量检查；涉及执行协议再补相关宿主纯文本测试。
4. 进入发布条件：F1／F2 通过；F4 通过或未验证风险经用户明确接受；候选交付检查完成。经授权推送后还需 F3 全绿，才创建正式 Release；之后补正式附件 F5 安装冒烟。
5. 没有堆内存证明本身不是故障；已有证据外的范围如实注明，不承诺“绝对无 Bug”。未通过项不能改写成通过。

简要顺序：**两个疑点 → 旧前端冒烟／边界确认 → 候选包检查 → 授权推送与 CI → 授权发布及安装冒烟。**
